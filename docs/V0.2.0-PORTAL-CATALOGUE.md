# v0.2.0 Portal Expansion Catalogue

> Research deliverable for v0.2.0 multi-portal expansion. **No implementation in v0.1.0.x.** This is a reference doc enumerating Microsoft 365 portal endpoints available via nodoc OpenAPI specs.

## Scope

**v0.1.0 GA baseline (frozen at tag `v0.1.0`)**: 64 streams (63 live + 1 deprecated) across Microsoft Defender XDR portal-internal APIs. 1,153 paths across 23 nodoc-defender-xdr/ specs.

**v0.2.0 scope** (operator directive 2026-05-08): more Defender streams + multi-portal expansion. v0.2.0 ships AS-IS for v0.1.0 GA scope; v0.2.0 only adds NEW work, no v0.1.0 cleanup.

## Source

All catalogue data derives from `.internal/nodoc-reference/specifications/` (gitignored research cache). Path counts include all HTTP methods on all paths in each spec.

## v0.2.0a — More Defender streams (highest immediate ROI)

Defender XDR baseline at v0.1.0 GA = 64 streams covering ~595 of 1,153 nodoc paths. Remaining ~558 paths are candidates for v0.2.0a inclusion. High-value categories:

- **TVM expansion** (vulnerability_management.yml) — additional sub-endpoints (recommendation tasks, remediation per machine, security baselines per profile).
- **Threat Analytics outbreaks** — `/mtp/threatAnalytics/outbreaks` endpoint not yet covered.
- **Multi-tenant operations** — additional MtoOps endpoints beyond the 3 covered today.
- **EndpointConfig deferred streams** — 4 streams previously dropped per `release.yml` grep-gate ("NO_PUBLIC_API"): MDE_AsrRulesConfig_CL, MDE_AntiRansomwareConfig_CL, MDE_ControlledFolderAccess_CL, MDE_NetworkProtectionConfig_CL — re-investigate with nodoc cross-check.
- **Architecture A PerEntityFanout** — DeviceTimeline canonical path `GET /mtp/mdeTimelineExperience/machines/{MachineId}/events` requires per-machine iteration. Foundation: MDE_Machines_CL inventory stream (already live in v0.1.0 GA).

## v0.2.0b — Entra portal expansion

**Primary research: nodoc-ibiza-iam (34 specs, 476 paths)**

Sample operations:
- `devices.yml` — sync devices, RoamingSettings, device creation
- `authentication_methods.yml` — TOTP, FIDO2, Windows Hello registrations
- `groups.yml` — group membership changes, dynamic group rules
- `applications.yml` — app registrations, secrets, certificates
- `enterprise_apps.yml` — service principals, OAuth grants
- `gdpr.yml` — data subject requests

**Specialty stubs** (need subdivision):
- `nodoc-entra-b2c/` — B2C user flows, custom policies (6 paths)
- `nodoc-entra-idgov/` — Identity Governance (14 paths)
- `nodoc-entra-iga/` — Identity & Access (9 paths)
- `nodoc-entra-pim/` — Privileged Identity Management (14 paths)

**v0.2.0b prerequisites**:
1. Entra portal auth chain — sccauth equivalent for `iam.hosting.portal.azure.net` (different from Defender XDR `security.microsoft.com`)
2. New DCR category `Defender_Entra_*_CL` workspace tables
3. Manifest module structure — likely a new `Xdr.Entra.Client` PowerShell module mirroring `Xdr.Defender.Client`

## v0.2.0c — Purview (Compliance) portal expansion

**Research gap**: nodoc-purview-portal/ is a 8-path stub. Primary research lives in nodoc-purview/specification/.

## v0.2.0 prerequisites identified by audit

1. **Multi-tenant FA scoping** — current single-tenant Function App constraint. Pre-v0.2.0: per-tenant secret namespace + XdrTierState PartitionKey extension.
2. **Architecture A PerEntityFanout** — DeviceTimeline per-machine implementation deferred from v0.1.0 GA. Required for portal-fanout patterns (e.g., per-user Entra sign-in detail iteration).
3. **DCR consolidation 13 → 7-8** — current 13 DCRs sharing 1 DCE will reshape when category split logic incorporates new portals.
4. **Per-portal manifest module structure** — likely 4 new modules: `Xdr.Entra.Client`, `Xdr.Purview.Client`, `Xdr.Intune.Client`, `Xdr.M365Admin.Client` (each mirroring `Xdr.Defender.Client`).
5. **Architecture E OpenAPI fixture generator** — already built (`tools/Generate-FixtureFromOpenApi.ps1`); v0.2.0 will exercise it for license-gated streams across portals.

## Live testing plan for v0.2.0

For each new portal added in v0.2.0:
1. Capture live response per endpoint via `tools/Capture-EndpointSchemas.ps1` (extend for portal-specific auth).
2. Generate ProjectionMap from response shape.
3. Add manifest entry + workspace table cols + DCR streamDecl.
4. Verify via `Verify-EndToEndProduction.ps1` per portal.
5. Document live SuccessKind classification per stream in `XdrConnectorHealth_CL.Reason`.
